# 10월 30일 회의용 — 구현과 BAG_RAW 재처리

가져갈 결론: **색·영상 반쪽을 바꾸며 선을 갈아타는 방식에서, 좌우 경계의 역할을 추적하고 하나의 중심 경로를 유지하는 구조로 바꿨다.**
카메라 보정과 지연 방지까지 연결한 실행 가능한 개선 후보다. 급커브·지그재그 완주를 해결한 단계는 아니다.

## 실제 구현물

- `lane_detection_fusion/core.py`: 여러 높이의 선 후보 연결, 시간상 좌우 대응, 최근 두 선에서 학습한 영상 폭, 한 선 중심 복원, 명시적인 소실·불확실 정지.
- `geometry.py`와 `config/camera_calibration.json`: 선배 카메라 ZIP의 실제 K/D 값 사용. raw1280×720 → 보정 → 640×360. 이미 보정된 영상은 재보정 생략.
- `runtime.py`와 `node.py`: 입력 대기 1장, 별도 추론 작업, 원 영상 시각·수신 시각에 따른 처리 전후 폐기, 중단 경합 차단, 독립 정지 감시.
- `config/profile.json`: 코드와 환경 설정 분리. 영상 P + 경로 방향 항, D 기본 0, I 없음. 조향 요구·관측 품질·한 선 상태에 따른 감속.
- 기본 실행은 `/lane_fusion/cmd_vel_preview`만 발행하며 `/lane_state=false`. 실제 로봇을 구동하지 않았다.

## 검증 범위

입력은 **새 BAG_RAW의 /camera_raw_16_9**만 사용했다. 이전 normal/unnormal의 수치는 제외했다.
수동 조종 명령은 정답으로 쓰지 않았다. 아래는 모든 기록 프레임을 순서대로 넣어 만든 새 코드의 계산 결과다.

| 새 코드의 인지 상태 | raw normal | raw reverse |
| --- | ---: | ---: |
| 전체 처리 | 2,755 | 2,642 |
| 두 경계 사용 | 944 | 804 |
| 왼쪽 경계 관측 + 최근 폭 | 276 | 236 |
| 오른쪽 경계 관측 + 최근 폭 | 294 | 293 |
| 역할·폭·품질 불확실 → 정지 | 694 | 731 |
| 유효 곡선 없음 → 정지 | 547 | 578 |

**이 비율은 인식 정확도나 주행 성공률이 아니다.** 실내 준비·비주행 장면도 들어 있으며, 선을 잘못 선택한 결과가 `both`로 나올 수 있다.
모든 프레임의 명령은 유한값 검사에 통과했다. 카메라 입력이 새 명령에 따라 바뀌는 폐루프 실험은 하지 않았다.
전체 `frames.csv`, 설정·코드 해시가 담긴 `summary.json`, 입력/추정 비교 `replay.mp4`를 각 `raw_*_v1` 폴더에 보존했다.

분석 PC에서 JPEG 디코딩+보정+인지 계산의 p95는 normal **30.01ms**, reverse **30.96ms**였다.
두 기록을 별도 프로세스에서 동시에 처리한 측정이다. 영상 렌더링·저장 시간은 제외하며 **로봇의 카메라→구동기 지연 측정이 아니다**.

자동 검사 **27건 통과**: 양쪽/한쪽 중심 일관성, 좌우 조향 부호, 소실 시 정지, 오래된 역할 폐기,
입력 교체, 추론 전후 만료, 중단·모드 변경 경합, 독립 감시, 원 header 수명, 시계 전진·역행 등.
Python 3.8 문법 검사와 패키지 메타데이터 검사도 통과했다. 로컬 실행은 Python 3.12/OpenCV 5.0이다.
Galactic/Python 3.8/OpenCV 4.2의 실제 ROS 빌드·메시지 연동·실차 주행은 미검증이다.

## 실제 확인하고 수정한 문제

초기 normal 80장이 모두 ambiguous였다. 한 페인트의 양쪽 대비 에지가 서로 다른 선 후보로 잡혀
‘여러 차로가 존재’한다고 판정한 것이 원인이었다. 같은 밝기 띠의 에지를 합치는 처리를 넣은 뒤 같은 80장이 모두 `both`가 됐다.
이 장면을 보고 수정했으므로 **미사용 데이터 성능으로 보고하지 않는다**.
넓은 반사 덩어리를 억제하되 선처럼 좁고 길게 생긴 반사까지 구별했다고 주장하지 않는다.

## 아직 남아 있는 핵심 실패

1. **normal 약145초**: 두 경계가 영상에 보이는데도 ambiguous로 정지한다. 급격한 굽음에서 후보 연결·관측 길이·이전 역할 대응 조건이 동시에 깨질 수 있다. 정확한 기여는 추가 분해 실험이 필요하다.
2. 한 선만 보인 상태에서 새로 시작하거나 이전 폭이 오래되면 좌우를 임의로 정하지 않고 정지한다. 초기 두 선 확인이 필요하다.
3. 영상상의 행별 폭은 카메라 요·피치·차체 위치에 영향을 받는다. 오래된 폭으로 급커브를 계속 달리는 방식에는 한계가 있다.
4. 낮은 품질에서는 속도가 매우 작아진다. 실제 구동계의 움직이기 시작하는 속도와 조향 응답을 측정해 감속 범위를 정해야 한다.

독립 검토는 `INDEPENDENT_REVIEW.md`, 원본 흰선 코드의 새 BAG_RAW 비교는 `BASELINE_RAW.md`에 있다.
baseline과 새 코드의 영상 준비·좌표계가 달라 픽셀값이나 명령 진폭만 단순 비교하면 안 된다.

원본 흰선 코드도 같은 새 BAG_RAW 전체에서 다시 실행했다. 유효 성분이 없어 `center=640`을 쓰는 fallback은
normal 531장, reverse 525장이며, 이 중 각각 531장·502장에서 새 주행 명령을 계산했다.
reverse의 조기 return 34장은 주로 준비 장면 등에 있고, 요청한 reverse 64–92초 지그재그에는 return이 없었다.
이는 원본의 ‘없어도 중심값으로 계속 계산’하는 코드 경로를 재현한 결과이며 사고·주행 실패 횟수가 아니다.

## 회의에서 볼 장면

- `zigzag_normal.mp4`: raw normal 140–155초. 해결되지 않은 급지그재그 포함.
- `zigzag_reverse.mp4`: raw reverse 64–92초. 경계 소실·재확인과 S 구간.
- `contact_sheet.jpg`: 정상·한 선·정지·급곡선의 표본 모음.
- 각 전체 영상의 왼쪽은 원본 입력, 오른쪽은 선배 보정값과 새 추정 경로다. 기존 원본 코드와 나란히 비교한 영상은 아니다.

## 다음 구현의 우선순위

1. 지금 남은 정지 장면을 기준으로 선 후보 연결과 시간 대응의 실패를 각각 분해한다. 정지 비율을 줄이려고 역할·폭 검사를 통째로 풀지 않는다.
2. 카메라 높이·각도와 지면 대응점을 측정해 지면 기하를 얻은 뒤, 실제 폭과 거리 기반 경로 추종을 별도 비교한다.
3. 좁고 긴 반사가 계속 후보로 남으면 해당 실패 구간만 우선 라벨링해서 세그멘테이션을 후보 생성기로 비교한다. 경계 역할 추적과 지연 방지 구조는 유지한다.
4. 새 경기장 bag의 연속 구간 일부는 보류하고 설정 후보를 선택한다. 보류 구간과 실차 저속 시험 후 프로필을 확정한다.

**아직 없는 기능**: bag 자동 파라미터 탐색·최적화, 실제 카메라 노출 제어, YOLO 학습, 미터 기반 Pure Pursuit/MPC.
환경 프로필은 재시작 시 읽으며 런타임 ROS 파라미터 변경은 거부한다. ‘bag 넣으면 최적값 자동 적용’이 완성된 상태는 아니다.

새 로컬 Git 저장소 이름은 `lane_detection_fusion`이다. 연결된 GitHub 도구에는 새 저장소 생성 기능이 없어 조직 원격 저장소는 아직 만들지 못했다.
기존 조직 저장소와 원본 코드는 수정하지 않았다. 코드·설정·검증 자료는 로컬 제출 ZIP으로 전달한다.
